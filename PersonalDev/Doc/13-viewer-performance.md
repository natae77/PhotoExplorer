# 13. 뷰어 성능 문제 조사와 수정

"특정 동영상을 재생하면 앱 전체가 느려진다"는 신고에서 출발해, **원인이 그 동영상이 아니라
사진 로딩 방식**임을 밝히고 고친 기록이다.

- 작성일: 2026-08-29
- 프로젝트: **PhotoExplorer** (`natae77/PhotoExplorer`)
- 브랜치: `feature/media-view-mode`
- 실기기: SM-F971N (Galaxy Z Fold 7), Android 17, 420dpi, release(R8) 빌드
- 상태: **수정 완료. 실기기에서 사용자 확인까지 마쳤다** (§9)

**개정 이력**

| 개정 | 날짜 | 무엇이 바뀌었나 |
|---|---|---|
| 1차 | 2026-08-29 | 최초 작성 |
| 2차 | 2026-08-29 | §6 추가 — 문턱값을 낮추면서 드러난 HEIC 방향 회귀와 수정 |
| 3차 | 2026-08-29 | §9 추가 — 실기기 사용자 확인 결과. §4.2·§5의 "확인 못 함"을 닫음 |

## 1. 신고 내용과 실제 증상

처음 신고는 이랬다.

> `사진앨범/가족/IMG_6072.MOV` 의 재생이 굉장히 느리고, 이 파일을 재생하고 나면 앱 전체가 느려진다.

조사 중에 증상이 더 정확해졌다. **로딩이 느린 것이 아니었다.**

- 동영상: 프레임이 아주 잠깐 멈췄다가 이어지기를 반복한다
- 스와이프: **애니메이션이 부드럽지 않다.** 사진이 늦게 뜨는 것이 아니다
- 그 파일 하나가 아니라 **"그 부근에 가면"** 나타난다

이 셋이 모두 **프레임을 그리는 비용** 을 가리킨다. I/O가 아니다.

## 2. 지목된 파일은 죄가 없었다

`IMG_6072.MOV` — 1920×1080 HEVC(돌비 비전 `dvhe.08.05`), 6.07초, 364프레임(≈60fps), 9.8 MB.
트랙 7개(영상 1 + 오디오 1 + 타임드 메타데이터 `mebx` 5).

**파일 하나만 있는 폴더에 복사해서 열면 아무 문제가 없다.**

| | 탭 → 코덱 RUNNING | 재생 시작 | Graphics |
|---|---|---|---|
| `IMG_6072.MOV` 단독 | 0.1초 | 약 1.1초 | 134 MB |
| `IMG_6050.MOV` 단독 (대조군) | — | — | 142 MB |

돌비 비전도 문제가 아니었다. 로그에 `NoSupport [codec.profileLevel, dvhe.08.05]` 가 찍히지만
그건 **소프트웨어 디코더**가 못 한다는 뜻이고, 하드웨어 디코더(`c2.qti.hevc.decoder`)가
100 ms 만에 잡힌다.

> ⚠️ **처음에 한 대조 실험은 틀렸다.** `IMG_6072`는 양옆이 12MP HEIC 사진이고 `IMG_6050`은
> 양옆이 동영상이라, `offscreenPageLimit = 1` 때문에 **이웃 페이지가 메모리에 같이 올라온다.**
> 이걸 모르고 재면 "6072가 1.2 GB를 쓴다"는 잘못된 결론이 나온다. 이웃을 없애고 다시 재서
> 뒤집었다.

## 3. 진짜 원인 — 원본 해상도 비트맵

`MediaViewerAdapter`는 사진을 **원본 해상도 그대로** 디코딩해 `PhotoView`에 통째로 올린다.

타일링을 쓰는 `SubsamplingScaleImageView`로 넘기는 조건이 `width * height * 4 > 100 MB` 였는데,
**100 MB는 `RecordingCanvas`의 하드 리밋**(그릴 수 있느냐)이지 성능 기준이 아니다.

아이폰 12MP HEIC = 4032 × 3024 × 4 = **48.8 MB**. 하드 리밋 아래라 통짜 비트맵 경로를 탄다.
그리고 `offscreenPageLimit = 1`이라 **그런 페이지가 항상 3장 살아 있다.**

동영상이 끊기는 이유도 여기에 있다. 재생 화면은 `TextureView`이므로
([12번 §2.3](12-video-viewer-plan.md) — `DepthPageTransformer`가 `alpha`·`scale`을 걸기 때문에
`SurfaceView`를 못 쓴다) **앱의 렌더 스레드를 사진과 같이 쓴다.** 그 스레드가 48 MB짜리
비트맵 업로드로 막히면 영상 프레임이 그대로 멈춘다.

### 3.1 시스템이 직접 지목한다

앱을 새로 띄우고, **동영상을 한 번도 재생하지 않은 채** 사진 두 장 사이만 8초 스와이프한 결과다.

```
Total frames rendered: 219
Janky frames: 171 (78.08%)
Number Slow bitmap uploads: 171   ← 전부
Number Slow UI thread: 70
Number Missed Vsync: 123
```

실제 조작 중 그래픽 메모리는 이렇게 진동했다 — 한 장 넘길 때마다 수백 MB를 만들고 버린다.

```
16:15:43   73MB  ← 좌우 스와이프 시작
16:15:45 1060MB
16:15:47 1097MB
16:15:49  681MB
16:15:52 1173MB
16:15:54 1320MB  ← 최고점
16:15:58   52MB  ← 뷰어 나감
```

> ⚠️ **`dumpsys meminfo`는 대상 앱에 강제 GC를 유발한다.** 2초 간격으로 찍으면 로그에
> `Explicit concurrent mark compact GC`가 그 간격으로 찍히고, **측정이 증상을 악화시킨다.**
> 위 `gfxinfo` 수치는 meminfo를 찍지 않는 동안 잰 것이라 영향이 없다.

## 4. 수정 — 문턱값 하나

`shouldUseLargeImageView`의 기준을 **100 MB → 24 MB** 로 낮춰, 큰 사진이
**이미 쓰고 있던 타일링 뷰**로 가게 했다. 상수 이름도 `MAX_BITMAP_SIZE`(하드 리밋)에서
`LARGE_IMAGE_BITMAP_SIZE`(성능 기준)로 바꿨다.

새 코드가 아니라 **경로 전환**이라 위험이 낮고, 확대 화질은 타일링이 오히려 낫다.

### 4.1 결과 (실기기, release/R8, 같은 8초 스와이프)

| | 수정 전 | 수정 후 |
|---|---|---|
| Total frames rendered | 219 | **646** |
| Janky frames | 171 (**78.08%**) | 10 (**1.55%**) |
| 50th percentile | 61 ms | **5 ms** |
| 90th percentile | 121 ms | **6 ms** |
| Number Missed Vsync | 123 | **0** |
| **Number Slow bitmap uploads** | 171 | **0** |
| Graphics | 1,082 MB | **206 MB** |
| TOTAL PSS | 1,476 MB | **703 MB** |

같은 시간에 프레임이 219 → 646장. 애니메이션이 3배 촘촘해졌다.

### 4.2 동영상 끊김은 숫자로 증명하지 못했다

`gfxinfo`는 **`TextureView`로 그려지는 영상 프레임을 세지 않는다.** 재생 중 측정치가
`Total frames 0`으로 나와서 프레임 페이싱을 잴 수 없다.

다만 **끊김을 만들던 원인은 사라졌다** — 재생 화면에서 `Slow bitmap uploads: 0`,
`Slow UI thread: 0`. 최종 판단은 눈으로 봐야 했고, **실기기에서 확인했다** (§9).

## 5. 슬라이더를 끌 때 스피너가 뜨던 것

[11a §6.1](11a-viewer-ui-cleanup-spec.md)의 지연 표시가 **의도치 않게 걸리던 자리**다.

슬라이더를 끄는 동안 플레이어는 계속 `STATE_BUFFERING`에 있다. 손가락을 오래 두면 0.5초를
넘기고, 화면 한가운데 스피너가 뜬다. **탐색 중에는 그림을 봐야 하는데 스피너가 가린다.**

`DefaultTimeBar`의 `OnScrubListener`를 붙여, **손가락이 슬라이더에 있는 동안에는 버퍼링을
표시하지 않는다.** 스크럽이 시작되면 이미 예약된 표시도 취소한다.

> 이 수정은 **adb로 검증할 수 없었다.** `input swipe`로 스크럽을 흉내내면 컨트롤이 숨은
> 상태에서 `ViewPager2`의 페이지 넘김으로 먹힌다. 두 번 시도해 둘 다 실패했고,
> **실기기에서 사람이 직접 끌어 확인했다** (§9).

## 6. §4의 수정이 드러낸 것 — HEIC가 반시계 90도로 돌아간다

문턱값을 낮추자마자 **아이폰 사진 일부가 반시계 90도로 누워** 보였다. 원본 파일은 멀쩡했다.

### 6.1 어떤 파일이 돌아가는가

EXIF `Orientation` 값과 증상이 **정확히 일치**했다.

| 파일 | EXIF Orientation | 증상 |
|---|---|---|
| IMG_6070.HEIC | **6** (시계 90도 회전 필요) | 돌아감 |
| IMG_6071.HEIC | **6** | 돌아감 |
| IMG_6074.HEIC | **1** (그대로) | **정상** |
| IMG_6075.HEIC | **6** | 돌아감 |

**회전이 필요한 사진에만 회전이 적용되지 않는다.** 저장된 가로 픽셀이 그대로 나오니
기대한 세로 대비 반시계 90도로 보인다.

### 6.2 JPEG으로는 재현되지 않는다

EXIF `Orientation=6`을 넣은 4032×3024 JPEG을 만들어 열어 보면 **두 경로가 똑같이, 올바르게**
나온다. 즉 `SubsamplingScaleImageView`는 우리 `content://` URI에서 JPEG의 EXIF는 읽지만
**HEIC에서는 못 읽는다.**

> ⚠️ 이 함정 때문에 처음 재현 시도가 실패했다. **합성 JPEG으로는 이 버그를 못 잡는다.**
> 실제 아이폰 HEIC 표본이 있어야 한다.

### 6.3 수정 — 방향을 우리가 읽어서 넘긴다

`ORIENTATION_USE_EXIF`에 맡기지 않는다. `loadImageInfo()`가 이미 파일을 열어 크기를 읽고
있으므로, 그 자리에서 **`androidx.exifinterface`(이미 의존성에 있고 HEIF를 지원)** 로 방향도
읽어 `ImageInfo.rotationDegrees`에 담고, 뷰에 **각도를 직접 지정**한다.

이렇게 하면 라이브러리가 URI 스킴별로 EXIF를 어떻게 찾는지에 **의존하지 않게** 되어
HEIC·JPEG이 동일하게 동작한다.

덤으로 `cropScale`의 `orientation == ORIENTATION_90/270` 비교도 이제 실제로 맞는다.
예전에는 `orientation`이 `ORIENTATION_USE_EXIF`(-1)여서 그 분기가 **한 번도 참이 되지 않았다.**

### 6.4 검증 (에뮬레이터, Pixel 8 / API 36)

실기기에서 가져온 HEIC 두 장으로 확인했다.

| | 수정 전 | 수정 후 |
|---|---|---|
| `Orientation=6` 사진 | 반시계 90도로 누움 | **똑바로** |
| `Orientation=1` 사진 | 정상 | **정상** (이중 회전 없음) |

> 이 버그는 §4의 수정이 만든 것이 아니라 **원래 있던 것**이다. 예전에는 100 MB를 넘는 사진만
> 이 경로를 탔기 때문에 드러나지 않았을 뿐이다.

## 8. 아직 손대지 않은 것

효과가 부족하면 이 순서로 본다. **한 번에 하나씩.**

1. **썸네일용 하드웨어 디코더가 최대 5개까지 동시에 잡힌다.** 로그의
   `ResourceManagerService: addMediaInfo pid ... allocated hw codec count`가 재생용(1920×1080)
   외에 512×512·640×896을 계속 더한다. coil-video의 `MediaMetadataRetriever` 쪽이다
2. **`TextureView` → `SurfaceView`.** 영상 끊김에는 가장 확실하지만
   [12번 §2.3](12-video-viewer-plan.md)의 페이지 전환이 깨진다. 트랜스포머를 손보지 않는 한 못 쓴다
3. **`offscreenPageLimit`** — 줄이면 메모리는 덜 쓰지만 옆 페이지가 늦게 뜬다

## 9. 조사에서 배운 것

- **증상을 다시 물어야 한다.** "로딩이 느리다"로 알고 시작했지만 실제로는 "애니메이션이
  거칠다"였고, 그때부터 볼 곳이 완전히 달라졌다
- **대조군의 조건을 맞춰야 한다.** 양옆 페이지가 다르면 그 비교는 무효다 (§2)
- **계측이 증상을 만들 수 있다.** `dumpsys meminfo`의 강제 GC (§3.1)
- **`gfxinfo`의 `Number Slow bitmap uploads`가 결정적이었다.** 추측이 아니라 시스템이
  병목을 이름으로 알려준다
- **합성 표본으로는 못 잡는 버그가 있다.** 방향 회귀는 JPEG으로는 재현되지 않았고,
  실제 아이폰 HEIC를 가져와서야 잡혔다 (§6.2)
- **경로를 바꾸는 수정은 그 경로에 잠자던 버그를 깨운다.** 타일링 뷰는 원래도 EXIF를 제대로
  못 읽고 있었는데, 그 길로 가는 사진이 없어서 아무도 몰랐다
