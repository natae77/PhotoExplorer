# 10. 미디어 뷰어 — 아래로 끌어서 닫기

미디어 뷰어에서 아래로 끌면 **작은 이동 임계값까지는 사진이 움직이지 않고, 폴더로 돌아가는
제스처라고 확정된 뒤에는 누적된 손가락 이동량을 따라잡아 1:1로 내려간다.** 사진 아래에는 이미
돌아갈 폴더 화면이 보인다. 놓으면 닫히거나 제자리로 돌아온다.
사진 페이지와 동영상 페이지 모두에 적용한다.

이 문서는 기획과 구현 방법을 함께 담는다. 08·09번이나 11·12번처럼 나누지 않은 이유는 §7에 있다.

- 작성일: 2026-08-28 / 최종 개정: **2026-09-12 (8차)**
- 프로젝트: **PhotoExplorer** (`natae77/PhotoExplorer`, `zhanghai/MaterialFiles` fork)
- 대상 버전: 1.7.4 (versionCode 39) 기준 소스 + 동영상 뷰어(11·12번) 적용 후
- 상태: **8차 동작 및 폴더 뷰포트 동기화 구현 완료**

**개정 이력** — 이 문서는 개정할 때 새 문서를 만들지 않고 **본문을 직접 고친다.**

## 1. 배경 — 1~3차의 플릭 방식은 왜 실패했나

3차까지의 구현은 `GestureDetector.onFling` 하나에 얹혀 있었다. 실기기에서 써 보니
**세 번에 한 번꼴로 먹지 않았다.** 원인은 셋이고 전부 설계에 있었다.

**1. 손을 떼는 순간의 속도만 봤다.** `onFling` 은 그 순간의 속도만 준다. 사람은 스와이프 끝에서
속도를 줄이며 떼기 때문에, 아무리 길게 끌어도 뗄 때 느리면 아무 일도 일어나지 않았다.
**얼마나 내려갔는지는 아예 보지 않았다.**

**2. 임계값이 좌우 스와이프보다 4배 엄격했다.** `scaledMinimumFlingVelocity × 4` 를 썼다.
좌우 스와이프는 배수 없이 `minFlingVelocity` 그대로다(§3.1). 사용자는 좌우와 같은 세기로 긋는데
세로만 4배를 요구했다.

**3. 되먹임이 없었다.** 판정이 되든 안 되든 화면이 똑같아서 제대로 하고 있는지 알 방법이 없었다.
그래서 성공률이 65%든 95%든 **복불복으로 느껴진다.** 이것이 가장 큰 문제다.

1차 설계에서 드래그 추종을 "작업량·회귀 위험이 크다"며 배제했는데, **되먹임이 없다는 비용을
계산에 넣지 않은 판단**이었다. 4차에서 뒤집는다(D1).

## 2. 목표 / 비목표

**목표**

1. 아래로 끌 때 작은 이동량 임계값 전에는 사진이 고정되고, 제스처가 확정되면 **누적 이동량을 따라잡은 뒤 손가락과 1:1로 움직인다.**
2. 놓았을 때 **충분히 내려갔거나 충분히 빠르면** 뒤로가기와 동일하게 닫힌다. 아니면 제자리로 돌아온다.
3. 사진이 움직이는 동안 빈 검정 화면이 아니라 **현재 미디어 타일이 화면 안에 준비된 실제 폴더 화면이 사진 아래에 이미 보인다.**
4. 닫힘 판정의 거리·속도 기준은 좌우 스와이프를 기준으로 유지한다(§3). 시작 임계값은 작아서 동작이 뻑뻑하게 느껴지면 안 된다.
5. 사진 페이지와 동영상 페이지에서 똑같이 동작한다.
6. 기존 조작을 건드리지 않는다 — 좌우 페이지 넘김, 탭으로 앱 바·컨트롤 토글, 더블탭 확대,
   확대 후 끌기, 재생 슬라이더 드래그.

**비목표 (이번 범위 아님)**

- 위로 끌기에 기능 부여(예: 세부 정보 열기).
- 텍스트 뷰어 등 다른 뷰어 화면.
- 제스처 켜기/끄기 설정 항목.
- 재생 중 세로로 끌어 밝기·음량 조절.

## 3. 동작 정의

### 3.1 좌우 스와이프는 어떻게 판정하는가 (기준으로 삼는 것)

`ViewPager2` 는 내부적으로 `RecyclerView` + **`PagerSnapHelper`** 를 쓴다.
`viewpager2-1.1.0-beta02` / `recyclerview-1.4.0` 바이트코드로 확인한 실제 동작이다.

| | 값 |
|---|---|
| 드래그 시작 | `touchSlop` 을 넘으면 |
| 끄는 동안 | **페이지가 손가락을 따라 움직인다** |
| 놓을 때 — 거리 | `PagerSnapHelper.findSnapView()` → `findCenterView()`. **화면 중앙에 가장 가까운 페이지**로 붙는다. 별도 상수가 없고, 실질 기준은 **페이지 폭의 50%** |
| 놓을 때 — 속도 | `SnapHelper.onFling()` 이 `RecyclerView.getMinFlingVelocity()`(= `ViewConfiguration.getScaledMinimumFlingVelocity()`, 50dp/s 상당)와 비교 |
| 판정 | **거리 또는 속도, 둘 중 하나** |

### 3.2 아래로 끌기 — 같은 모델로 맞춘다

| | 좌우 (ViewPager2) | 아래 (이 문서) |
|---|---|---|
| 드래그 시작 | `touchSlop` | `touchSlop` **그리고** 세로 이동이 가로의 1.5배 이상 |
| 끄는 동안 | 페이지가 손가락과 거의 1:1로 따라옴 | 시작 임계값 전에는 사진 고정. 확정 순간 누적 이동량을 따라잡고 이후 **손가락과 1:1로 이동** + 폴더 화면 선노출 + 축소·반투명 |
| 거리 기준 | 페이지 폭의 50% | 화면 높이의 **12.5%** |
| 속도 기준 | `minFlingVelocity` | **동일** (배수 없음). 단 **5% 이상 이동**했을 때만 |
| 판정 | 둘 중 하나 | **둘 중 하나** |

**표의 “같은 모델”은 닫힘 판정에 관한 말이다.** 5차의 차이는 시간 지연이 아니라 아래로
돌아가려는 의도가 확인될 때까지 사진을 고정하는 작은 이동량 임계값이다.
거리만 50%가 아니라 12.5%인 이유는, 좌우는 **다음 페이지가 보이며 들어오는** 동작이지만 아래로는
**화면 밖으로 내보내는** 동작이라 절반까지 끌게 하면 손이 화면을 벗어나기 때문이다(D6).

**드래그를 시작하지 않는 경우**

| 상황 | 동작 |
|---|---|
| 사진이 확대된 상태 | 기존 pan 그대로. 페이지는 움직이지 않는다 |
| 좌우로 끌 때 | 기존 페이지 넘김 그대로 (세로가 가로의 1.5배 미만이면 우리 것이 아니다) |
| 위로 끌 때 | 아무 일도 없음 |
| 두 손가락 | 기존 핀치 줌 그대로 |
| **재생 컨트롤 위에서 시작** | 컨트롤이 먹는다. 페이지까지 내려오지 않는다(§4.4) |
| **"다른 앱으로 열기" 버튼 위** | 버튼이 먹는다 |
| 사진 로딩 실패·로딩 중 | 끌 수 있다. 붙잡고 있을 내용이 없으므로 막을 이유가 없다 |

**재생 중에 닫으면** — 뒤로가기와 동일한 경로를 타므로 재생 정지·플레이어 해제는 기존 처리가
그대로 한다. 재생 위치는 세션이 끝나므로 잊고(11번 §5.4), 배속은 1×로 돌아간다(11번 §6.3).

**닫는 방법** — `activity.onBackPressedDispatcher.onBackPressed()`. `finish()` 가 아니다(D4).
이 프로젝트는 이미 같은 디스패처를 쓴다
([FragmentExtensions.kt:38](../app/src/main/java/me/zhanghai/android/files/util/FragmentExtensions.kt#L38)).

### 3.3 아래 스와이프의 순서 — 이동량으로 확정한 뒤 따라잡는다

5차에서 말하는 `delay`는 **시간 지연도, 사진이 손가락 뒤를 계속 쫓는 효과도 아니다.** 아래의 작은
이동량 임계값을 넘기 전까지 사진을 움직이지 않아, 좌우 페이지 넘김이나 탭과 구분하는 구간이다.

1. DOWN 뒤 세로 이동량이 작은 임계값에 못 미치면 사진은 제자리에 둔다. 경과 시간은 보지 않는다.
2. `ACTION_POINTER_DOWN`이 한 번이라도 오면 그 터치 스트림은 마지막 UP/CANCEL까지 거부한다.
   이미 드래그 중이었다면 닫힘 판정 없이 복귀한다.
3. 임계값을 넘었고 세로 이동이 가로의 1.5배 이상이면 “폴더로 돌아가기” 제스처로 확정한다.
4. 같은 처리에서 검정 window background의 알파를 낮춰 아래 폴더 화면을 드러낸다.
5. 사진의 `translationY`를 `(현재 rawY - downRawY).coerceAtLeast(0f)` 전체 값으로 설정해, 임계값 구간에 누적된
   손가락 이동량까지 **즉시 따라잡는다.** `touchSlop`을 빼지 않는다.
6. 이후 MOVE에서는 같은 하한식을 써 사진이 손가락과 1:1로 움직인다. 별도의 보간·지연 애니메이션은 없다.
7. 손을 떼면 UP 이벤트에서 실제 이동량을 다시 계산해 거리·플릭 최소거리 판정에 쓴다.
   취소되면 사진과 검정 배경을 함께 복원한다.

이 순서라면 시간과 무관하게 같은 이동량에서 시작하고, 사진이 처음 움직이는 화면에는 이미 폴더
화면이 보인다. 임계값은 방향을 판단할 수 있을 정도로만 작게 두고 실기기에서 조정한다(D13).

### 3.4 사진 아래에 보이는 화면

PhotoExplorer의 파일 목록에서 뷰어를 열었을 때는 별도 액티비티인 `FileListActivity`가 바로 아래에 있다.
뷰어 창은 반투명으로 만들되 `windowBackground`는 **검정 `ColorDrawable`**로 유지한다. 아래 스와이프가
확정되면 이 drawable의 알파를 낮춰 실제 폴더 화면을 드러낸다. 정지된 스크린샷을 새로 만드는 방식이
아니므로 선택 상태·날짜 타일 등은 실제 `FileListActivity`의 현재 상태와 정확히 같다.

다만 **스크롤 위치는 좌우 페이지가 정착할 때 의도적으로 동기화한다.** 현재 미디어 타일이 폴더
뷰포트 밖이면, 뷰어가 아직 불투명한 동안 폴더를 그 타일이 보이는 위치로 미리 옮긴다. 따라서 아래
스와이프를 시작했을 때는 사용자가 처음 떠나온 위치가 아니라 **지금 보고 있는 미디어가 보이는 실제
폴더 화면**이 첫 프레임부터 나타난다. 이미 타일이 보이면 폴더 위치를 바꾸지 않는다.

이 플래그와 viewport session은 `FileListFragment.openMediaViewer()`에서
`viewType == MEDIA && shared-element options != null`인 내부 실행에만 넣는다. 현재처럼 모든 내부
동영상 실행에 넣지 않으며, 리스트·바둑판 동영상은 검정 배경의 기존 닫기를 유지한다. 공용
`maybeAddMediaViewerExtras()`에도 넣지 않는다. 외부 앱의 `VIEW` 인텐트처럼 아래에 PhotoExplorer
폴더 화면이 없는 진입에서는 다른 앱 화면을 드러내지 않고 기존 검정 배경을 유지한다.
공유 요소 복귀 전환과의 접합은 [18번 §3.6.1](18-shared-element-transition-plan.md)에서 다룬다.

### 3.5 좌우로 넘길 때 폴더 위치도 미리 맞춘다

이 동작은 공유 요소 전환이 있는 **MEDIA 모드의 내부 진입에만** 적용한다. 리스트·바둑판 모드에서
연 동영상, 외부 `VIEW`와 공유 요소 없이 연 뷰어는 아래 목록을 움직이지 않는다.

1. `ViewPager2`가 `SCROLL_STATE_IDLE`이 되어 현재 페이지가 확정된다.
2. 뷰어는 현재 경로를 아래 폴더에 알린다. 빠른 플링 중 지나간 `onPageSelected`마다 보내지 않는다.
3. 폴더는 해당 타일 전체가 이미 보이면 그대로 두고, 일부라도 뷰포트 밖일 때만 즉시 스크롤한다. 사용자가 볼 수 없는
   불투명 뷰어 아래이므로 `smoothScroll`은 쓰지 않는다.
4. 다음 pre-draw에서 타일 holder가 붙고 전체 사각형이 RecyclerView 뷰포트 안에 든 것을 확인한 뒤
   viewport READY를 돌려준다.
5. 현재 페이지와 READY 경로가 일치할 때만 아래 스와이프가 폴더를 드러낸다.

타일의 **자리와 크기**가 준비되면 viewport READY다. 썸네일 drawable 로딩까지 기다리면 원격·대용량 폴더에서
제스처 준비가 불필요하게 늦으므로 요구하지 않는다. 준비 중인 상태에서 곧바로 아래로 끌면 사진을
제자리에 두고, READY가 된 뒤 같은 터치 스트림의 다음 MOVE에서 누적 이동량을 따라잡아 시작한다.
이것은 시간으로 제스처를 지연하는 규칙이 아니라, 잘못된 폴더를 노출하지 않기 위한 화면 준비 조건이다.
타일이 삭제됐거나 폴더 화면이 없어서 준비할 수 없으면 드래그 중에는 검정 배경을 유지한다. 손을
놓아 닫을 때는 18번 §3.4.5의 최종 준비를 한 번 더 시도하고, 그것도 실패했을 때만 일반 전환으로 끝낸다.

## 4. 구현

### 4.1 판정은 **페이지 루트 한 곳**에서 한다

3차까지는 터치를 받는 뷰가 세 가지라 세 군데에 각각 붙였다. 4차에서는 페이지의 **루트**를
전용 레이아웃으로 바꿔 한 곳으로 모은다. 페이지 전체가 움직여야 하니 루트가 맞는 자리다.

```
SwipeDownDismissLayout   ← 세로 드래그를 가로채고, 자기 자신을 움직인다
├─ (사진)   PhotoView / SubsamplingScaleImageView / progress / errorText
└─ (동영상) PlayerView / thumbnailImage / progress / errorLayout
```

[SwipeDownDismissLayout.kt](../app/src/main/java/me/zhanghai/android/files/viewer/media/SwipeDownDismissLayout.kt)

- `onInterceptTouchEvent` 에서 §3.2의 시작 조건을 보고 가로챈다. 가로챈 뒤에는
  `parent.requestDisallowInterceptTouchEvent(true)` 로 `ViewPager2` 가 도로 뺏지 못하게 한다.
- 시작 임계값 전에는 페이지를 움직이지 않는다. 확정되는 MOVE에서 `translationY`를
  `(rawY - downRawY).coerceAtLeast(0f)` 전체 값으로 설정하고, 이후에도 같은 식으로 1:1로 따른다.
- 드래그 시작·진행·취소를 프래그먼트로 알려 검정 window background를 사진의 첫 이동과
  **같은 프레임에 이미 보이게** 하고, 취소 시 사진과 함께 복원한다(§4.5).
- 사진 자체의 `alpha`는 1로 유지한다. 드래그 끝에서 공유 요소가 불투명해질 때 생기는 밝기 점프를 막는다.
- 놓을 때 §3.2의 규칙으로 닫거나 되돌린다. 닫을 때는 **되돌리지 않고 그 자리에 둔다** —
  액티비티 종료 애니메이션이 이어받는다(D12).
- `canDismiss: () -> Boolean` 을 밖에서 받아, 내용이 그 제스처를 필요로 하는지 물어본다.

### 4.2 ⚠️ `SubsamplingScaleImageView` 는 부모의 가로채기를 막는다

SSIV는 터치를 잡을 때마다 부모에게 `requestDisallowInterceptTouchEvent(true)` 를 건다
(3.10.0 바이트코드에 6곳). 그 플래그가 서면 **`onInterceptTouchEvent` 가 아예 호출되지 않는다.**
그대로 두면 대용량 이미지 페이지에서는 드래그를 시작조차 못 한다.

그래서 레이아웃이 그 요청을 **선별해서 받는다.**

```kotlin
override fun requestDisallowInterceptTouchEvent(disallowIntercept: Boolean) {
    if (disallowIntercept && !isDragging && canDismiss()) {
        return   // 확대 안 된 상태의 요청은 무시한다
    }
    super.requestDisallowInterceptTouchEvent(disallowIntercept)
}
```

확대 중이면 `canDismiss()` 가 false이므로 요청이 그대로 전달되어 pan이 정상 동작한다.
`PhotoView`(2.3.0)와 `PlayerView`(media3 1.11.0)는 이 요청을 **하지 않는다**(둘 다 0곳).

### 4.3 확대 판정 — 뷰 종류별로 다르다

사진 페이지의 `canDismiss` 는 지금 보이는 뷰에 따라 갈린다
([MediaViewerAdapter.kt](../app/src/main/java/me/zhanghai/android/files/viewer/media/MediaViewerAdapter.kt)).

| 보이는 뷰 | 조건 |
|---|---|
| `PhotoView` | `scale <= 1 × 1.01` — PhotoView의 배율은 **화면에 맞춘 상태가 1** 이다 |
| `SubsamplingScaleImageView` | `isReady && scale <= minScale × 1.01` |
| 둘 다 안 보임(로딩 중·오류) | `true` — 붙잡을 내용이 없다 |

어느 뷰를 쓸지는 `shouldUseLargeImageView` 가 정한다(픽셀×4 > 100MB, 또는 2048px 초과 + 비율 2:1 이상).
**두 갈래를 모두 확인해야 한다.** 한쪽만 보면 "어떤 사진은 되고 어떤 사진은 안 되는" 버그가 된다.

### 4.4 동영상 페이지

확대·이동이 없으므로 `canDismiss` 는 항상 `true` 다.

**재생 컨트롤과는 자동으로 분리된다.** `PlayerControlView` 는 페이지가 아니라 **프래그먼트
레이아웃**에 있고 `ViewPager2` 위에 겹쳐 있다
([media_viewer_fragment.xml](../app/src/main/res/layout/media_viewer_fragment.xml), 12번 §4.1).
컨트롤 영역에서 시작한 터치는 컨트롤이 가져가므로 페이지까지 내려오지 않는다.
**슬라이더를 아래로 끌어도 닫히지 않는다.** 따로 막을 코드가 필요 없다(D10).

### 4.5 시작 임계값과 폴더 화면 선노출 (5차 구현)

별도 타이머나 `Choreographer` 보간은 추가하지 않는다. 기존 `shouldStartDrag()`의 `touchSlop`과
방향 조건이 곧 “폴더로 돌아가기” 판정 임계값이다. 이 값은 기기별 터치 특성에 맞춰 Android가
제공하는 작은 이동량이므로 우선 그대로 사용하고, 실기기에서 너무 크다고 느껴질 때만 별도 dp 상수로
낮춘다.

4차 구현은 드래그가 시작된 MOVE에서 `touchSlop`을 빼므로 사진이 0부터 움직였다.

```kotlin
setDragOffset((event.rawY - downRawY - touchSlop).coerceAtLeast(0f))
```

5차 구현에서는 빼지 않았다. 확정 순간
`setDragOffset((event.rawY - downRawY).coerceAtLeast(0f))`를 호출해 임계값을 넘는 동안 쌓인
이동량을 한 번에 따라잡고, 이후 MOVE도 같은 식으로 손가락과 1:1로 맞춘다. UP에서는
`finalOffset`을 같은 식으로 다시 계산해 12.5% 거리와 5% 속도 판정 최소거리에 사용한다.

한 번이라도 `ACTION_POINTER_DOWN`을 받은 스트림은 `gestureRejected`로 표시한다. 임계값 전이면
그대로 자식의 핀치 줌에 맡기고, 이미 드래그 중이면 `animateBack()`으로 전환해 닫힘을 금지한다.
마지막 UP/CANCEL 전에는 포인터가 다시 하나가 되어도 아래 스와이프를 재개하지 않는다.

레이아웃은 다음 콜백을 어댑터를 거쳐 프래그먼트에 전달한다.

| 콜백 | 프래그먼트 동작 |
|---|---|
| `onDragStarted(page)` | 현재 페이지이고 `REVEAL_READY(sessionId, sequence, path)`일 때만 검정 window background를 옅게 한다. `BLACK_FALLBACK`은 255 유지 |
| `onDragProgress(page, progress)` | `REVEAL_READY`인 같은 페이지·sequence일 때만 실제 이동 진행률에 맞춰 배경을 더 투명하게 한다 |
| `onDragCancelled(page)` | 사진과 같은 200ms·같은 interpolator로 배경 알파를 255로 복원한다 |
| `onDismissed(page)` | 배경 복원 animator를 취소하고 현재 상태를 18번 복귀 전환으로 넘긴다 |

기존 `Theme.MaterialFiles.Immersive`는 `MediaViewerActivity`만 사용하므로 새 테마 이름을 만들지 않고
Material 2·3의 Immersive base에 `windowIsTranslucent=true`를 추가한다. 검정 `windowBackground`는
그대로 둔다. 새 이름을 만들면 `CustomThemeHelper`가 요구하는 색상·Material3·Black 파생 스타일을
전부 추가해야 하므로 피한다.

내부 폴더 진입 extra가 없는 외부 `VIEW` 진입에서는 진행 콜백을 받아도 window background를
불투명하게 유지한다.
외부 앱이나 런처 화면이 사진 아래로 드러나는 것은 기능 범위가 아니며 개인정보 측면에서도 피한다.

배경 알파는 확정 순간 85%(폴더 15% 노출)로 바꾸고, 실제 이동량이 화면 높이의 12.5%에 도달하면
0%가 되도록 선형으로 낮춘다. 사진 이동과 배경 변경은 같은 MOVE 처리에서 적용해 **첫 이동 프레임에
이미 폴더가 보이게** 한다. 별도 한 프레임 선행은 만들지 않는다. 시스템 바는 1차 구현에서 뷰어가
계속 소유하며, 드래그 중 모양을 바꾸지 않는다.

배경 제어 소유자는 현재 페이지 하나뿐이다. 콜백의 `page`가 `currentPageRoot()`와 다르면 무시하고,
새 드래그·페이지 변경·뷰 파괴 시 기존 배경 animator를 취소한 뒤 알파를 255로 복원한다.

### 4.6 폴더 뷰포트 선행 동기화 구현 계획 (7차)

세부 구조는 [18번 §3.4](18-shared-element-transition-plan.md)에 둔다. 핵심 계약은 다음과 같다.

- `FileListFragment.openMediaViewer()`가 MEDIA 모드 내부 실행마다 고유 `sessionId`를 만들고 intent에
  넣는다. 프로세스 내부 `MediaViewerViewportCoordinator`가 이 세션만 연결하며 외부 진입에는 없다.
- 뷰어는 `publishCurrentViewportIfIdle()` 하나를 최초 pager pre-draw, scroll state의 IDLE 진입,
  paths 삭제·replace와 currentItem 보정 직후에 호출한다. coordinator가 세션별로 1, 2, 3처럼
  증가하는 `sequence`를 발급하므로 뷰어 재생성으로 번호가 되감기지 않는다.
- 폴더는 `sessionId + sequence + path`가 최신 요청인지 pre-draw에서 다시 확인하고
  `READY` 또는 `UNAVAILABLE`을 응답한다. A→B→C의 늦은 B 콜백은 아무것도 하지 않는다.
- `SwipeDownDismissLayout`은 기존 확대용 `canDismiss`와 별도로 `WAIT / REVEAL_READY /
  BLACK_FALLBACK` 시작 상태를 받는다. WAIT이면 사진을 고정하고, REVEAL_READY이면 정상 선노출하며,
  BLACK_FALLBACK이면 사진 드래그는 허용하되 검정 배경을 유지한다.
- 폴더 뷰 재생성 시 같은 세션으로 다시 등록해 최신 요청을 replay한다. listener는 뷰 생명주기에 맞춰
  `onViewCreated`부터 `onDestroyView`까지 등록해 PAUSED 상태에서도 수신하고, 종료·새 뷰어 실행 때
  세션을 폐기한다. coordinator는 액티비티나 프래그먼트를 장기 보관하지 않는다.
- adapter data·정렬·span/layout 변화와 view 파괴는 기존 READY를 WAIT으로 무효화하고 최신 요청을
  다시 검사한다. 목록 로딩 중에는 즉시 실패시키지 않고 제한 시간 안에서 pre-draw/데이터 갱신을 기다린다.
- 최종 `onActivityReenter()`의 현재 경로 확인과 스크롤은 제거하지 않는다. 선행 준비가 무효화됐거나
  실패한 경우에도 한 번 더 준비하는 마지막 안전망이며, 그것도 실패했을 때만 일반 전환으로 끝낸다.

### 4.7 값

| 이름 | 값 | 왜 |
|---|---|---|
| `DISMISS_FRACTION` | `0.125f` | 화면 높이의 12.5%. D6 |
| `FLICK_MIN_FRACTION` | `0.05f` | 속도로 닫으려면 최소 이만큼은 내려가 있어야 한다. 짧은 떨림만으로 닫히지 않게 하는 하한이다 |
| 속도 문턱 | `ViewConfiguration.scaledMinimumFlingVelocity` | 좌우 스와이프와 동일. 배수 없음 |
| `DIRECTION_RATIO` | `1.5f` | 세로가 가로의 1.5배 이상일 때만 가져간다 |
| 시작 임계값 | 우선 `touchSlop` | 시간과 무관한 작은 이동량. 너무 크다고 느껴질 때만 별도 dp 값으로 낮춘다 |
| `BACKGROUND_ALPHA_AT_DRAG_START` | `0.85f` | 확정 순간 폴더 화면이 인지되도록 15% 노출 |
| 배경 알파 끝 | 실제 이동량 12.5%에서 `0f` | 닫힘 거리 기준에 도달하면 폴더 화면을 전부 표시 |
| `MAX_SCALE_DOWN` | `0.2f` | 다 내렸을 때 80% 크기. 사진 alpha는 줄이지 않는다 |
| `ANIMATE_BACK_DURATION` | `200L` | 복귀 애니메이션 |

전부 상수로 빼 두었다. 손맛은 실기기에서 조정한다.

### 4.9 ⚠️ 구현하면서 걸린 것 둘

둘 다 처음에는 "제스처가 아예 안 먹는다"로 보였고, 원인이 전혀 달랐다.

**1. 동영상 페이지에서는 `onInterceptTouchEvent` 가 호출되지 않는다.**
`ViewGroup.dispatchTouchEvent` 는 `mFirstTouchTarget`(터치를 가져간 자식)이 있을 때만 인터셉트
단계를 다시 탄다. 동영상 페이지에는 터치를 먹는 자식이 없다 — `PlayerView` 는
`use_controller="false"` 라 자기 컨트롤러를 안 쓰고 썸네일은 그냥 `ImageView` 다. 그래서 루트가
클릭 대상으로서 DOWN을 직접 소비하고, **그 뒤 MOVE는 인터셉트를 건너뛰고 `onTouchEvent` 로 바로 온다.**
사진 페이지는 `PhotoView`/`SSIV` 가 DOWN을 먹으므로 인터셉트가 정상 호출된다.
→ **드래그 시작 판정을 `onInterceptTouchEvent` 와 `onTouchEvent` 양쪽에 둔다.**

**2. `VelocityTracker` 에 이벤트를 그대로 넣으면 속도가 0으로 나온다.**
`MotionEvent` 의 좌표는 그 뷰 기준인데, **페이지가 손가락을 따라 움직이므로 뷰 안에서 손가락은
거의 제자리다.** 아무리 빨리 그어도 속도가 문턱을 못 넘어 거리 조건으로만 닫혔다.
→ `MotionEvent.obtain()` 으로 복사해 `setLocation(rawX, rawY)` 로 **화면 좌표를 넣는다.**

이 둘은 "드래그 추종" 방식에만 생기는 문제다. 3차까지의 플릭 방식은 뷰를 움직이지 않았고
`GestureDetector` 가 속도를 알아서 계산했으므로 겪을 일이 없었다.

### 5.1 ⚠️ `adb shell input swipe` 로는 손맛을 검증할 수 없다

3차 때 에뮬레이터와 실기기에서 자동 테스트 24건을 전부 통과시켰는데, **정작 사람이 쓰니 3분의 1이
안 먹혔다.** `input swipe` 가 만드는 제스처는 **등속으로 그어지고 끝까지 속도를 유지한 채 떼지는**,
플릭 판정에 가장 유리한 입력이기 때문이다. 사람 손가락은 끝에서 감속한다.

**자동 테스트로 확인할 수 있는 것은 "조건을 만족하면 동작하는가" 까지다.**
"사람이 자연스럽게 그었을 때 되는가"는 반드시 손으로 봐야 한다.

느린 드래그는 `input swipe` 의 지속 시간을 길게 주면 흉내낼 수 있다
(화면 40%를 1.5초에 — `input swipe 624 400 624 1190 1500`). 거리 기준이 동작하는지는 이것으로 확인된다.
드래그 중간 화면을 보려면 `input motionevent DOWN/MOVE` 로 손가락을 붙잡아 둔 채 캡처한다.

실제로 확인한 것 — 에뮬레이터(Pixel 8 / API 36), 디버그 빌드, 2026-08-28.

| 묶음 | 건수 | 결과 |
|---|---|---|
| 동영상 페이지 (느린 40%·아주 느린 40%·빠른 플릭 12%·느린 10% 복귀·6% 복귀·위로) | 6 | 전부 통과 |
| 사진 두 경로 (느린 40% 닫힘, 10% 복귀) | 3 | 전부 통과 |

드래그가 손가락을 따라오는지는 `input motionevent DOWN/MOVE` 로 중간에 멈춰 세운 뒤
화면 위쪽 픽셀이 검게 드러나는 것으로 확인했다.

### 5.2 자동 검증에서 걸린 함정

**1. 기존 테스트 이미지로는 `PhotoView` 경로를 하나도 못 덮는다.**
`photo_*.png` · `emu*.png` 가 전부 1080×2400이다. 세로가 2048을 넘고 비율이 0.45라
§4.3의 조건에 걸려 **죄다 `SubsamplingScaleImageView` 로 간다.** 가로·세로가 모두 2048 이하이거나
비율이 0.5~2 인 이미지를 따로 만들어야 한다(1200×900을 썼다).

**2. 1080×2400 이미지는 더블탭해도 확대되지 않는다.**
화면과 크기가 같아 `cropScale == minScale` 이라 확대할 여지가 없다. 확대 가드를 검사하려면
비율이 극단적인 이미지가 필요하다(4000×1000을 썼다 — 최소 배율 0.27, 더블탭 배율 2.4).

**3. 더블탭 자동화는 3분의 1쯤 실패한다.**
`adb shell "input tap X Y; sleep 0.15; input tap X Y"` 가 그나마 되는 형태지만
(붙여 쓰면 합쳐지고, adb 호출을 나누면 간격이 벌어진다) **그래도 6회 중 2회는 무동작이었다.**
확대 상태를 화면 픽셀로 확인하고 될 때까지 재시도해야 한다. 이걸 안 하면
"확대가 안 된 상태로 테스트하고 통과했다"고 착각한다.

**4. Fold 7은 화면이 둘이라 `mCurrentFocus` 가 두 번 나온다.** 첫 번째가 `null` 이라
`grep -m1` 로 잡으면 항상 null이다. `dumpsys activity activities | grep topResumedActivity` 를 쓴다.

**5. 폰에서는 `adb exec-out screencap -p` 가 잘린다.** `screencap -p /sdcard/x.png` 로 저장한 뒤
`adb pull` 해야 온전한 PNG를 얻는다.

## 6. 수용 기준 (Acceptance Criteria)

**되먹임**

1. 작은 이동량 임계값 전에는 사진이 움직이지 않는다. 같은 거리를 움직이면 걸린 시간과 무관하게 같은 지점에서 시작한다.
2. 임계값을 넘는 순간 사진이 그동안 누적된 이동량을 따라잡고, 이후에는 손가락과 1:1로 움직인다.
3. 사진이 처음 움직이는 프레임에는 그 아래에 **검정 빈 화면이 아니라 돌아갈 폴더 화면이 이미 보인다.**
4. 조금만 내리고 놓으면 사진과 검정 window background가 같은 200ms 동안 **함께 제자리로 돌아온다.**
5. 실제 손가락 이동이 12.5% 이상이면 속도와 무관하게 닫힌다. 손을 멈춘 채 떼도 닫힌다.
6. 5% 이상 빠르게 움직이면 12.5%를 못 채워도 닫힌다. 5% 미만 입력은 속도와 관계없이 취소된다.
7. 외부 `VIEW` 인텐트로 연 뷰어에서는 아래 앱·런처가 드러나지 않고 검정 배경을 유지한다.

**세 경로 모두**

8. 보통 크기 사진(`PhotoView`), 대용량 사진(`SubsamplingScaleImageView`), 동영상 페이지에서
   똑같이 동작하고 **손맛이 같다.**

**기존 동작**

9. 좌우 스와이프로 페이지가 넘어간다. 비스듬히 넘겨도 닫히지 않는다.
10. 탭하면 앱 바와 컨트롤이 토글된다(사진·동영상 모두).
11. 더블탭 확대 후 아래로 끌면 **이미지가 이동(pan)만 하고 페이지는 움직이지 않는다.**
   대용량 사진에서도 그렇다(§4.2가 동작해야 한다).
12. 두 손가락 핀치 줌 중에 페이지가 움직이지 않는다.
13. 재생 컨트롤이 보일 때 **슬라이더를 아래로 끌어도 닫히지 않는다.**
14. 동영상 재생 중에 닫으면 소리가 남지 않고 플레이어가 해제된다.
15. 페이지를 넘긴 뒤 다시 끌어도 정상이다(재활용된 페이지에 이전 드래그·프레임 콜백이 묻어나지 않는다).
16. 좌우 스와이프가 IDLE로 끝났을 때 현재 미디어 타일이 화면 밖이면, 아래 폴더가 그 타일이 보이는
    위치로 미리 이동한다. 이미 보이는 타일이면 폴더 위치가 바뀌지 않는다.
17. 여러 페이지를 빠르게 넘기면 최종 IDLE 페이지 하나만 반영되고, 늦은 이전 요청이 폴더를 되돌리지 않는다.
18. IDLE 직후 곧바로 아래로 끌어도 이전 미디어 타일이 보이지 않는다. 현재 타일 READY 전에는 사진이
    움직이지 않고, READY 후에는 누적 이동량을 따라잡아 시작한다.
19. 타일 삭제·폴더 재생성·준비 실패 시 잘못된 타일을 보이지 않고 검정 배경의 일반 복귀로 폴백한다.

## 8. 브랜치 (기록)

1~3차 구현은 `feature/swipe-down` 에 있었고, 동영상 뷰어 작업이 대상 파일을 `MediaViewer*` 로
바꿔 놓아 그대로 합쳐지지 않았다. **`feature/video-viewer` 위로 리베이스**해서 정리했고, 이후
`feature/media-view-mode` 에 fast-forward로 합쳤다.

리베이스에서 나온 것 — 비슷한 이름 변경이 또 있을 때 쓸 수 있다.

| 파일 | 무슨 일이 있었나 |
|---|---|
| `ImageViewerAdapter.kt` → `MediaViewerAdapter.kt` | **git이 이름 변경을 스스로 찾아냈다.** 내용 충돌 세 군데만 났다 |
| `ImageViewerFragment.kt` → `MediaViewerFragment.kt` | **못 찾았다.** 내용이 너무 많이 바뀌어(220줄 → 575줄) 유사도 기준에 못 미쳤다. `modify/delete` 충돌로 떨어져 손으로 옮겼다 |

⚠️ **이름 변경을 따라간 자동 병합이 코드를 두 번 넣을 수 있다.** `companion object` 의 상수가
중복 선언돼 컴파일이 깨졌고(`Conflicting declarations`), **컴파일이 통과하는 중복**도 하나 있었다
(같은 리스너를 두 번 등록 — 두 번째가 첫 번째를 덮어써서 동작은 정상이었다).
충돌 표시가 없는 자리라 눈에 띄지 않는다. **표시를 다 지운 뒤에도 반드시 컴파일하고 diff를 읽어야 한다.**
