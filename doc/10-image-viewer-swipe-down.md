# 10. 미디어 뷰어 — 아래로 끌어서 닫기

미디어 뷰어에서 **아래로 끌면 화면이 손가락을 따라 내려가고, 놓으면 닫힌다.**
사진 페이지와 동영상 페이지 모두에 적용한다.

이 문서는 기획과 구현 방법을 함께 담는다. 08·09번이나 11·12번처럼 나누지 않은 이유는 §7에 있다.

## 1. 배경 — 1~3차의 플릭 방식은 왜 실패했나

3차까지의 구현은 `GestureDetector.onFling` 하나에 얹혀 있었다. 실기기에서 써 보니
**세 번에 한 번꼴로 먹지 않았다.** 원인은 셋이고 전부 설계에 있었다.

**1. 손을 떼는 순간의 속도만 봤다.** `onFling` 은 그 순간의 속도만 준다. 사람은 스와이프 끝에서
속도를 줄이며 떼기 때문에, 아무리 길게 끌어도 뗄 때 느리면 아무 일도 일어나지 않았다.
**얼마나 내려갔는지는 아예 보지 않았다.**

**2. 임계값이 좌우 스와이프보다 4배 엄격했다.** `scaledMinimumFlingVelocity × 4` 를 썼다.
좌우 스와이프는 배수 없이 `minFlingVelocity` 그대로다(§3.1). 사용자는 좌우와 같은 세기로 긋는데
세로만 4배를 요구했다.

**3. 되먹임이 없었다.** 판정이 되든 안 되든 화면이 똑같아서 제대로 하고 있는지 알 방법이 없었다.
그래서 성공률이 65%든 95%든 **복불복으로 느껴진다.** 이것이 가장 큰 문제다.

1차 설계에서 드래그 추종을 "작업량·회귀 위험이 크다"며 배제했는데, **되먹임이 없다는 비용을
계산에 넣지 않은 판단**이었다. 4차에서 뒤집는다(D1).

## 2. 목표 / 비목표

**목표**

1. 아래로 끌면 **페이지가 손가락을 따라 움직여** 진행 정도가 보인다.
2. 놓았을 때 **충분히 내려갔거나 충분히 빠르면** 뒤로가기와 동일하게 닫힌다. 아니면 제자리로 돌아온다.
3. 판정 기준을 **좌우 스와이프와 같게** 맞춘다(§3). 한쪽만 유독 뻑뻑하면 안 된다.
4. 사진 페이지와 동영상 페이지에서 똑같이 동작한다.
5. 기존 조작을 건드리지 않는다 — 좌우 페이지 넘김, 탭으로 앱 바·컨트롤 토글, 더블탭 확대,
   확대 후 끌기, 재생 슬라이더 드래그.

**비목표 (이번 범위 아님)**

- 위로 끌기에 기능 부여(예: 세부 정보 열기).
- 텍스트 뷰어 등 다른 뷰어 화면.
- 제스처 켜기/끄기 설정 항목.
- 재생 중 세로로 끌어 밝기·음량 조절.

## 3. 동작 정의

### 3.1 좌우 스와이프는 어떻게 판정하는가 (기준으로 삼는 것)

`ViewPager2` 는 내부적으로 `RecyclerView` + **`PagerSnapHelper`** 를 쓴다.
`viewpager2-1.1.0-beta02` / `recyclerview-1.4.0` 바이트코드로 확인한 실제 동작이다.

| | 값 |
|---|---|
| 드래그 시작 | `touchSlop` 을 넘으면 |
| 끄는 동안 | **페이지가 손가락을 따라 움직인다** |
| 놓을 때 — 거리 | `PagerSnapHelper.findSnapView()` → `findCenterView()`. **화면 중앙에 가장 가까운 페이지**로 붙는다. 별도 상수가 없고, 실질 기준은 **페이지 폭의 50%** |
| 놓을 때 — 속도 | `SnapHelper.onFling()` 이 `RecyclerView.getMinFlingVelocity()`(= `ViewConfiguration.getScaledMinimumFlingVelocity()`, 50dp/s 상당)와 비교 |
| 판정 | **거리 또는 속도, 둘 중 하나** |

### 3.2 아래로 끌기 — 같은 모델로 맞춘다

| | 좌우 (ViewPager2) | 아래 (이 문서) |
|---|---|---|
| 드래그 시작 | `touchSlop` | `touchSlop` **그리고** 세로 이동이 가로의 1.5배 이상 |
| 끄는 동안 | 페이지가 따라옴 | **페이지가 따라옴** + 내려간 만큼 축소·반투명 |
| 거리 기준 | 페이지 폭의 50% | 화면 높이의 **25%** |
| 속도 기준 | `minFlingVelocity` | **동일** (배수 없음). 단 **10% 이상 이동**했을 때만 |
| 판정 | 둘 중 하나 | **둘 중 하나** |

거리만 50%가 아니라 25%인 이유는, 좌우는 **다음 페이지가 보이며 들어오는** 동작이지만 아래로는
**화면 밖으로 내보내는** 동작이라 절반까지 끌게 하면 손이 화면을 벗어나기 때문이다(D6).

**드래그를 시작하지 않는 경우**

| 상황 | 동작 |
|---|---|
| 사진이 확대된 상태 | 기존 pan 그대로. 페이지는 움직이지 않는다 |
| 좌우로 끌 때 | 기존 페이지 넘김 그대로 (세로가 가로의 1.5배 미만이면 우리 것이 아니다) |
| 위로 끌 때 | 아무 일도 없음 |
| 두 손가락 | 기존 핀치 줌 그대로 |
| **재생 컨트롤 위에서 시작** | 컨트롤이 먹는다. 페이지까지 내려오지 않는다(§4.4) |
| **"다른 앱으로 열기" 버튼 위** | 버튼이 먹는다 |
| 사진 로딩 실패·로딩 중 | 끌 수 있다. 붙잡고 있을 내용이 없으므로 막을 이유가 없다 |

**재생 중에 닫으면** — 뒤로가기와 동일한 경로를 타므로 재생 정지·플레이어 해제는 기존 처리가
그대로 한다. 재생 위치는 세션이 끝나므로 잊고(11번 §5.4), 배속은 1×로 돌아간다(11번 §6.3).

**닫는 방법** — `activity.onBackPressedDispatcher.onBackPressed()`. `finish()` 가 아니다(D4).
이 프로젝트는 이미 같은 디스패처를 쓴다
([FragmentExtensions.kt:38](../app/src/main/java/me/zhanghai/android/files/util/FragmentExtensions.kt#L38)).

## 4. 구현

### 4.1 판정은 **페이지 루트 한 곳**에서 한다

3차까지는 터치를 받는 뷰가 세 가지라 세 군데에 각각 붙였다. 4차에서는 페이지의 **루트**를
전용 레이아웃으로 바꿔 한 곳으로 모은다. 페이지 전체가 움직여야 하니 루트가 맞는 자리다.

```
SwipeDownDismissLayout   ← 세로 드래그를 가로채고, 자기 자신을 움직인다
├─ (사진)   PhotoView / SubsamplingScaleImageView / progress / errorText
└─ (동영상) PlayerView / thumbnailImage / progress / errorLayout
```

[SwipeDownDismissLayout.kt](../app/src/main/java/me/zhanghai/android/files/viewer/media/SwipeDownDismissLayout.kt)

- `onInterceptTouchEvent` 에서 §3.2의 시작 조건을 보고 가로챈다. 가로챈 뒤에는
  `parent.requestDisallowInterceptTouchEvent(true)` 로 `ViewPager2` 가 도로 뺏지 못하게 한다.
- 끄는 동안 자기 `translationY` 를 손가락에 맞추고, 내려간 비율만큼 `scaleX/Y` 와 `alpha` 를 줄인다.
- 놓을 때 §3.2의 규칙으로 닫거나 되돌린다. 닫을 때는 **되돌리지 않고 그 자리에 둔다** —
  액티비티 종료 애니메이션이 이어받는다(D12).
- `canDismiss: () -> Boolean` 을 밖에서 받아, 내용이 그 제스처를 필요로 하는지 물어본다.

### 4.2 ⚠️ `SubsamplingScaleImageView` 는 부모의 가로채기를 막는다

SSIV는 터치를 잡을 때마다 부모에게 `requestDisallowInterceptTouchEvent(true)` 를 건다
(3.10.0 바이트코드에 6곳). 그 플래그가 서면 **`onInterceptTouchEvent` 가 아예 호출되지 않는다.**
그대로 두면 대용량 이미지 페이지에서는 드래그를 시작조차 못 한다.

그래서 레이아웃이 그 요청을 **선별해서 받는다.**

```kotlin
override fun requestDisallowInterceptTouchEvent(disallowIntercept: Boolean) {
    if (disallowIntercept && !isDragging && canDismiss()) {
        return   // 확대 안 된 상태의 요청은 무시한다
    }
    super.requestDisallowInterceptTouchEvent(disallowIntercept)
}
```

확대 중이면 `canDismiss()` 가 false이므로 요청이 그대로 전달되어 pan이 정상 동작한다.
`PhotoView`(2.3.0)와 `PlayerView`(media3 1.11.0)는 이 요청을 **하지 않는다**(둘 다 0곳).

### 4.3 확대 판정 — 뷰 종류별로 다르다

사진 페이지의 `canDismiss` 는 지금 보이는 뷰에 따라 갈린다
([MediaViewerAdapter.kt](../app/src/main/java/me/zhanghai/android/files/viewer/media/MediaViewerAdapter.kt)).

| 보이는 뷰 | 조건 |
|---|---|
| `PhotoView` | `scale <= 1 × 1.01` — PhotoView의 배율은 **화면에 맞춘 상태가 1** 이다 |
| `SubsamplingScaleImageView` | `isReady && scale <= minScale × 1.01` |
| 둘 다 안 보임(로딩 중·오류) | `true` — 붙잡을 내용이 없다 |

어느 뷰를 쓸지는 `shouldUseLargeImageView` 가 정한다(픽셀×4 > 100MB, 또는 2048px 초과 + 비율 2:1 이상).
**두 갈래를 모두 확인해야 한다.** 한쪽만 보면 "어떤 사진은 되고 어떤 사진은 안 되는" 버그가 된다.

### 4.4 동영상 페이지

확대·이동이 없으므로 `canDismiss` 는 항상 `true` 다.

**재생 컨트롤과는 자동으로 분리된다.** `PlayerControlView` 는 페이지가 아니라 **프래그먼트
레이아웃**에 있고 `ViewPager2` 위에 겹쳐 있다
([media_viewer_fragment.xml](../app/src/main/res/layout/media_viewer_fragment.xml), 12번 §4.1).
컨트롤 영역에서 시작한 터치는 컨트롤이 가져가므로 페이지까지 내려오지 않는다.
**슬라이더를 아래로 끌어도 닫히지 않는다.** 따로 막을 코드가 필요 없다(D10).

### 4.5 값

| 이름 | 값 | 왜 |
|---|---|---|
| `DISMISS_FRACTION` | `0.25f` | 화면 높이의 25%. D6 |
| `FLICK_MIN_FRACTION` | `0.1f` | 속도로 닫으려면 최소 이만큼은 내려가 있어야 한다. `minFlingVelocity` 가 50dp/s로 낮아, 이게 없으면 **10%를 1.5초에 걸쳐 천천히 끈 것(167px/s)까지 닫힌다**(실측) |
| 속도 문턱 | `ViewConfiguration.scaledMinimumFlingVelocity` | 좌우 스와이프와 동일. 배수 없음 |
| `DIRECTION_RATIO` | `1.5f` | 세로가 가로의 1.5배 이상일 때만 가져간다 |
| `MAX_SCALE_DOWN` / `MAX_FADE` | `0.2f` / `0.5f` | 다 내렸을 때 80% 크기, 50% 불투명 |
| `ANIMATE_BACK_DURATION` | `200L` | 복귀 애니메이션 |

전부 상수로 빼 두었다. 손맛은 실기기에서 조정한다.

### 4.7 ⚠️ 구현하면서 걸린 것 둘

둘 다 처음에는 "제스처가 아예 안 먹는다"로 보였고, 원인이 전혀 달랐다.

**1. 동영상 페이지에서는 `onInterceptTouchEvent` 가 호출되지 않는다.**
`ViewGroup.dispatchTouchEvent` 는 `mFirstTouchTarget`(터치를 가져간 자식)이 있을 때만 인터셉트
단계를 다시 탄다. 동영상 페이지에는 터치를 먹는 자식이 없다 — `PlayerView` 는
`use_controller="false"` 라 자기 컨트롤러를 안 쓰고 썸네일은 그냥 `ImageView` 다. 그래서 루트가
클릭 대상으로서 DOWN을 직접 소비하고, **그 뒤 MOVE는 인터셉트를 건너뛰고 `onTouchEvent` 로 바로 온다.**
사진 페이지는 `PhotoView`/`SSIV` 가 DOWN을 먹으므로 인터셉트가 정상 호출된다.
→ **드래그 시작 판정을 `onInterceptTouchEvent` 와 `onTouchEvent` 양쪽에 둔다.**

**2. `VelocityTracker` 에 이벤트를 그대로 넣으면 속도가 0으로 나온다.**
`MotionEvent` 의 좌표는 그 뷰 기준인데, **페이지가 손가락을 따라 움직이므로 뷰 안에서 손가락은
거의 제자리다.** 아무리 빨리 그어도 속도가 문턱을 못 넘어 거리 조건으로만 닫혔다.
→ `MotionEvent.obtain()` 으로 복사해 `setLocation(rawX, rawY)` 로 **화면 좌표를 넣는다.**

이 둘은 "드래그 추종" 방식에만 생기는 문제다. 3차까지의 플릭 방식은 뷰를 움직이지 않았고
`GestureDetector` 가 속도를 알아서 계산했으므로 겪을 일이 없었다.

### 5.1 ⚠️ `adb shell input swipe` 로는 손맛을 검증할 수 없다

3차 때 에뮬레이터와 실기기에서 자동 테스트 24건을 전부 통과시켰는데, **정작 사람이 쓰니 3분의 1이
안 먹혔다.** `input swipe` 가 만드는 제스처는 **등속으로 그어지고 끝까지 속도를 유지한 채 떼지는**,
플릭 판정에 가장 유리한 입력이기 때문이다. 사람 손가락은 끝에서 감속한다.

**자동 테스트로 확인할 수 있는 것은 "조건을 만족하면 동작하는가" 까지다.**
"사람이 자연스럽게 그었을 때 되는가"는 반드시 손으로 봐야 한다.

느린 드래그는 `input swipe` 의 지속 시간을 길게 주면 흉내낼 수 있다
(화면 40%를 1.5초에 — `input swipe 624 400 624 1190 1500`). 거리 기준이 동작하는지는 이것으로 확인된다.
드래그 중간 화면을 보려면 `input motionevent DOWN/MOVE` 로 손가락을 붙잡아 둔 채 캡처한다.

실제로 확인한 것 — 에뮬레이터(Pixel 8 / API 36), 디버그 빌드, 2026-08-28.

| 묶음 | 건수 | 결과 |
|---|---|---|
| 동영상 페이지 (느린 40%·아주 느린 40%·빠른 플릭 12%·느린 10% 복귀·6% 복귀·위로) | 6 | 전부 통과 |
| 사진 두 경로 (느린 40% 닫힘, 10% 복귀) | 3 | 전부 통과 |
| 확대 가드 (SSIV·PhotoView 확대 중 40% 드래그) | 2 | 전부 통과 |
| 회귀 (좌우 넘김·대각선·슬라이더·탭 토글) | 4 | 전부 통과 |

드래그가 손가락을 따라오는지는 `input motionevent DOWN/MOVE` 로 중간에 멈춰 세운 뒤
화면 위쪽 픽셀이 검게 드러나는 것으로 확인했다.

### 5.2 자동 검증에서 걸린 함정

**1. 기존 테스트 이미지로는 `PhotoView` 경로를 하나도 못 덮는다.**
`photo_*.png` · `emu*.png` 가 전부 1080×2400이다. 세로가 2048을 넘고 비율이 0.45라
§4.3의 조건에 걸려 **죄다 `SubsamplingScaleImageView` 로 간다.** 가로·세로가 모두 2048 이하이거나
비율이 0.5~2 인 이미지를 따로 만들어야 한다(1200×900을 썼다).

**2. 1080×2400 이미지는 더블탭해도 확대되지 않는다.**
화면과 크기가 같아 `cropScale == minScale` 이라 확대할 여지가 없다. 확대 가드를 검사하려면
비율이 극단적인 이미지가 필요하다(4000×1000을 썼다 — 최소 배율 0.27, 더블탭 배율 2.4).

**3. 더블탭 자동화는 3분의 1쯤 실패한다.**
`adb shell "input tap X Y; sleep 0.15; input tap X Y"` 가 그나마 되는 형태지만
(붙여 쓰면 합쳐지고, adb 호출을 나누면 간격이 벌어진다) **그래도 6회 중 2회는 무동작이었다.**
확대 상태를 화면 픽셀로 확인하고 될 때까지 재시도해야 한다. 이걸 안 하면
"확대가 안 된 상태로 테스트하고 통과했다"고 착각한다.

**4. Fold 7은 화면이 둘이라 `mCurrentFocus` 가 두 번 나온다.** 첫 번째가 `null` 이라
`grep -m1` 로 잡으면 항상 null이다. `dumpsys activity activities | grep topResumedActivity` 를 쓴다.

**5. 폰에서는 `adb exec-out screencap -p` 가 잘린다.** `screencap -p /sdcard/x.png` 로 저장한 뒤
`adb pull` 해야 온전한 PNG를 얻는다.

## 6. 수용 기준 (Acceptance Criteria)

**되먹임**

1. 아래로 끌면 **페이지가 손가락을 따라 내려오고**, 내려온 만큼 작아지며 흐려진다.
2. 조금만 내리고 놓으면 **제자리로 돌아온다.**
3. 25% 이상 내리고 놓으면 **속도와 무관하게** 닫힌다. 손을 멈춘 채 떼도 닫힌다.
4. 짧게라도 빠르게 튕기면 25%를 못 채워도 닫힌다.

**세 경로 모두**

5. 보통 크기 사진(`PhotoView`), 대용량 사진(`SubsamplingScaleImageView`), 동영상 페이지에서
   똑같이 동작하고 **손맛이 같다.**

**기존 동작**

6. 좌우 스와이프로 페이지가 넘어간다. 비스듬히 넘겨도 닫히지 않는다.
7. 탭하면 앱 바와 컨트롤이 토글된다(사진·동영상 모두).
8. 더블탭 확대 후 아래로 끌면 **이미지가 이동(pan)만 하고 페이지는 움직이지 않는다.**
   대용량 사진에서도 그렇다(§4.2가 동작해야 한다).
9. 두 손가락 핀치 줌 중에 페이지가 움직이지 않는다.
10. 재생 컨트롤이 보일 때 **슬라이더를 아래로 끌어도 닫히지 않는다.**
11. 동영상 재생 중에 닫으면 소리가 남지 않고 플레이어가 해제된다.
12. 페이지를 넘긴 뒤 다시 끌어도 정상이다(재활용된 페이지에 이전 드래그가 묻어나지 않는다).

## 7. 왜 기획서/계획서를 나누지 않았나

08·09번과 11·12번은 정렬·캐시·플레이어 수명까지 건드리는 큰 작업이라 "무엇을"과 "어떻게"를
분리할 값어치가 있었다. 이 기능은 **새 파일 1개 + 고친 파일 4개**다. 두 문서로 나누면 양쪽을
오가며 읽는 비용만 늘어난다.

## 8. 브랜치 (기록)

1~3차 구현은 `feature/swipe-down` 에 있었고, 동영상 뷰어 작업이 대상 파일을 `MediaViewer*` 로
바꿔 놓아 그대로 합쳐지지 않았다. **`feature/video-viewer` 위로 리베이스**해서 정리했고, 이후
`feature/media-view-mode` 에 fast-forward로 합쳤다.

리베이스에서 나온 것 — 비슷한 이름 변경이 또 있을 때 쓸 수 있다.

| 파일 | 무슨 일이 있었나 |
|---|---|
| `ImageViewerAdapter.kt` → `MediaViewerAdapter.kt` | **git이 이름 변경을 스스로 찾아냈다.** 내용 충돌 세 군데만 났다 |
| `ImageViewerFragment.kt` → `MediaViewerFragment.kt` | **못 찾았다.** 내용이 너무 많이 바뀌어(220줄 → 575줄) 유사도 기준에 못 미쳤다. `modify/delete` 충돌로 떨어져 손으로 옮겼다 |

⚠️ **이름 변경을 따라간 자동 병합이 코드를 두 번 넣을 수 있다.** `companion object` 의 상수가
중복 선언돼 컴파일이 깨졌고(`Conflicting declarations`), **컴파일이 통과하는 중복**도 하나 있었다
(같은 리스너를 두 번 등록 — 두 번째가 첫 번째를 덮어써서 동작은 정상이었다).
충돌 표시가 없는 자리라 눈에 띄지 않는다. **표시를 다 지운 뒤에도 반드시 컴파일하고 diff를 읽어야 한다.**
