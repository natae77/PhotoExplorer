# 20. 대용량 폴더 캐시 에뮬레이터 테스트 계획과 1차 결과

- 작성일: 2026-10-01
- 대상 브랜치: `bugfix/large-folder-initial-load`
- 대상 환경: Pixel 8 AVD, Android API 36
- 관련 계획: [19번 폴더별 촬영 시각 캐시 계획](19-media-created-time-cache-plan.md)

## 1. 목적

5,000개 미디어가 있는 폴더에서도 일반 목록이 촬영 시각 분석 때문에 막히지 않는지, 미디어
모드에서 만든 폴더별 캐시가 재진입과 앱 재시작 뒤 재사용되는지 확인한다. 화면이 준비 전 순서로
보였다가 다시 정렬되지 않는지, 검색이나 모드 전환으로 작업을 취소했을 때 오래된 결과가 뒤늦게
나타나지 않는지도 확인한다.

이번 1차 실행은 기능이 이어지는지 확인한 시험이다. 원본 미디어 판독 횟수, 캐시 적중 횟수,
정렬 안정성처럼 계측이나 별도 데이터가 필요한 항목은 아직 통과로 판정하지 않는다.

## 2. 시간 측정의 정의

`am start -W`는 Activity 시작 완료까지만 측정한다. 5,000개 목록이나 MEDIA가 RecyclerView에
전달된 시점은 포함하지 않으므로 이를 목록 완료 시간으로 쓰지 않는다.

이 문서의 1차 결과에 적은 시간은 자동화 시작부터 특정 화면 상태를 `uiautomator dump`로 확인한
시점까지의 경과 시간이다. 따라서 다음 비용이 섞여 있다.

- 차가운 실행에서는 프로세스와 Activity 시작 시간
- 입력 명령 전달과 화면 갱신 대기
- `uiautomator dump` 자체의 고정 비용
- 호스트와 에뮬레이터의 스케줄링 지연

특히 같은 프로세스의 짧은 측정은 `uiautomator` 비용이 하한이어서 앱 내부 처리 시간으로 해석할
수 없다. 다음 실행부터는 `am start -W` 값과 UI 완료 관찰 시간을 별도 열에 기록하고, debug 계측
시각도 함께 남긴다.

## 3. 1차 실행 환경과 데이터

1. debug APK를 빌드해 Pixel 8 AVD에 설치했다.
2. `/sdcard/Download/PhotoExplorer-5000`에 **1,856바이트 PNG 5,000개**를 준비했다.
3. 파일들은 같은 원본을 복제한 것이므로 미디어 촬영 시각과 파일 내용이 사실상 동일하다.
4. 필요한 시나리오에서는 앱의 `no_backup/media_created_time_cache`를 비우고 프로세스를 종료해
   차가운 캐시 상태를 만들었다.
5. 화면 완료는 파일 수, 목록/미디어 셀, 검색 결과를 UI 계층에서 찾아 판정했다.

### 데이터의 한계

동일한 PNG 복제본만으로는 촬영 시각순과 수정 시각 fallback 순서가 서로 달라지는지 확실히
구분할 수 없다. 따라서 1차 실행에서 “MEDIA가 한 번에 나타남”을 관찰했더라도 잘못된 순서가
중간 프레임에 한 번도 노출되지 않았다고 증명하지는 못한다.

다음 실행에는 파일명·수정 시각·내장 촬영 시각의 순서가 서로 다르도록 만든 sentinel 파일을
최소 10개 섞는다. 오름차순과 내림차순에서 sentinel의 예상 위치를 미리 적고 화면 녹화 또는
연속 UI snapshot으로 중간 노출 여부를 확인한다.

아래 시간은 §2의 UI 판정 경과 시간이다. 서로 다른 시작 조건의 절대 성능 비교값으로 사용하지
않는다.

| 시나리오 | UI 판정 경과 | 관찰 결과 | 판정 |
|---|---:|---|---|
| 캐시 없는 차가운 LIST 첫 진입 | 4.803초 | 5,000개 표시. 캐시 디렉터리 자체가 생성되지 않음 | 일반 LIST가 촬영 시각 캐시에 접근하지 않음 확인 |
| LIST에서 첫 MEDIA 전환 | 9.667초 | MEDIA 완료 뒤 캐시 생성 | 기능 확인. 긴 준비 시간의 UX와 정렬 안정성은 추가 검증 필요 |
| 같은 프로세스에서 캐시된 MEDIA 재진입 | 3.093초 | MEDIA 표시 | `uiautomator` 비용이 하한이라 앱 처리 시간 및 원본 판독 0회는 미확인 |
| 프로세스 종료 뒤 캐시된 MEDIA 진입 | 5.161초 | MEDIA 표시 | 디스크 캐시가 있는 조건의 기능 확인. 원본 판독 0회는 미확인 |

| 캐시 없는 차가운 MEDIA 직접 진입: 첫 dump | 4.202초 | 파일 수, 목록 셀, MEDIA 셀이 모두 아직 없음 | 완성 전 임시 목록은 관찰되지 않았으나 긴 빈 로딩 구간 확인 |
| 캐시 없는 차가운 MEDIA 직접 진입: 완료 | 13.511초 | MEDIA 준비 완료 | 기능 확인. 처리 중 진행 정도는 표시되지 않음 |

최초 MEDIA 뒤 생성된 캐시 파일은 1개, **175,028바이트**였다.

### 리뷰 수정 뒤 핵심 재실행

저장 순서, 같은 폴더 분석 직렬화, `AtomicFile` 복구, 손상 파일 제거, 전체 파일 크기 경계,
일시적인 원본 판독 실패 비저장을 반영한 APK로 앱 데이터를 초기화하고 핵심 흐름을 다시
실행했다. 항목 식별자를 파일명 대신 전체 provider URI로 강화했기 때문에 캐시 크기는
**450,028바이트**로 증가했다.

| 시나리오 | UI 판정 경과 | 관찰 결과 |
|---|---:|---|
| 캐시 없는 차가운 LIST | 5.503초 | 5,000개 표시, 캐시 디렉터리 미생성 |
| 첫 MEDIA 전환 | 13.399초 | MEDIA 표시 완료 |
| 첫 MEDIA 캐시 저장 | 13.441초 | MEDIA 표시 직후 폴더 캐시 1개 확인 |
| 프로세스 종료 뒤 캐시된 MEDIA | 6.435초 | 디스크 캐시를 유지한 채 MEDIA 표시 |
| 변화 없는 폴더 재진입 | 별도 시간 판정 없음 | 캐시 mtime `1790866044` 유지, 재작성하지 않음 |

이 값도 `uiautomator` 비용이 포함된 기능 확인값이다. 첫 MEDIA와 캐시 적중의 원본 판독 횟수는
계측을 추가하기 전까지 성능 통과로 판정하지 않는다.

### 파일 작업 뒤 자동 갱신 확인

MEDIA가 `image_0105.png` 부근을 표시하는 상태에서 복사, 보이는 파일 삭제, 보이는 파일 이름
변경을 차례로 실행했다. 자동 갱신마다 보기 방식과 정렬값을 같은 값으로 다시 설정하면서 adapter를
비우던 동작을 제거하고, 수동 당겨서 새로고침이 아닌 `PathObserver` 갱신에서는
`SwipeRefreshLayout` 표시를 강제로 켜지 않도록 수정했다.

- 복사 뒤 첫 화면 항목은 계속 `image_0105.png`였다.
- `image_0110.png` 삭제 뒤에도 첫 화면 항목은 `image_0105.png`였고 삭제 항목만 사라졌다.
- `image_0115.png`를 `image_6115.png`로 변경한 뒤에도 같은 화면 위치를 유지했다.
- 세 경우 모두 UI 계층에 `ProgressBar`가 나타나지 않았다.

### 1차 결과에서 확인하지 못한 것

- 4.202초 첫 dump 전후의 짧은 프레임에 잘못된 MEDIA 순서가 노출되지 않았는지
- 같은 프로세스 및 재시작 뒤 원본 PNG 판독이 실제로 0회였는지
- LIST에서 MEDIA로 바꿀 때 기존 5,000개 기본 정보를 재사용했는지, 폴더를 다시 열거했는지
- 첫 MEDIA 표시 직후 비동기 캐시 저장이 완료되었는지
- 파일 하나만 바뀌었을 때 그 파일만 다시 판독했는지
- 빠른 검색어 변경과 연속 모드 전환에서 취소된 결과가 전혀 게시되지 않았는지
- 실제 기기의 저장소에서 체감 시간이 허용 가능한지

## 5. 다음 에뮬레이터 실행 시나리오

### A. 일반 LIST

1. 캐시 디렉터리와 앱 프로세스를 정리한다.
2. 이름순 LIST로 폴더를 연다.
3. `am start -W`와 5,000개 UI 완료 시간을 따로 기록한다.
4. 촬영 시각 원본 판독, 캐시 read/write가 모두 0회인지 계측으로 확인한다.
5. 캐시 디렉터리가 생성되지 않는지 확인한다.

### B. 차가운 MEDIA와 표시 안정성

1. sentinel을 포함한 폴더를 LIST로 연 뒤 MEDIA로 전환한다.
2. 기존 LIST가 유지되는지, 빈 화면으로 바뀌는지, 로딩 표시가 무엇인지 기록한다.
3. 처리 중 LIST 전환과 뒤로가기가 즉시 반응하는지 확인한다.
4. 화면 녹화 또는 연속 snapshot으로 준비 전 MEDIA 셀과 잘못된 sentinel 순서가 노출되는지
   확인한다.
5. MEDIA 완료 시간과 캐시 파일 생성 완료 시간을 따로 기록한다.
6. 차가운 MEDIA 직접 진입도 같은 방식으로 반복한다.

현재 구현은 정책이 바뀌면 새 `FileListLiveData`를 만들어 폴더를 다시 읽고, MEDIA 준비 중에는
완성되지 않은 값을 adapter에 적용하지 않는다. 따라서 순서가 바뀌는 목록 대신 빈 로딩 화면이
길게 보일 수 있다. “틀린 순서를 표시하지 않음”뿐 아니라 기존 화면 유지 여부, 취소 조작성,
준비 상태 안내도 수용 기준에 포함한다.

### C. 캐시 적중 계측

debug 빌드에서 다음 카운터를 한 시나리오마다 초기화하고 기록한다.

- `MediaCreatedTime.read()` 원본 판독 횟수
- 폴더 캐시 파일 read/write 횟수
- 항목 cache hit/miss 횟수
- 폴더 열거와 기본 `FileItem` 생성 횟수

기대값은 다음과 같다.

| 시나리오 | 원본 판독 | 캐시 read | cache miss |
|---|---:|---:|---:|
| LIST 첫 진입 | 0 | 0 | 0 |
| 첫 MEDIA | 지원 미디어 수 | 최대 1 | 지원 미디어 수 |
| 같은 프로세스 MEDIA 재진입 | 0 | 메모리 적중이면 0 | 0 |
| 프로세스 종료 뒤 MEDIA 재진입 | 0 | 1 | 0 |
| 한 파일 내용·크기·mtime 변경 | 1 | 최대 1 | 1 |

단순히 캐시 파일이 존재하거나 화면이 빨리 보인다는 이유로 cache hit를 판정하지 않는다.

### D. 부분 cache miss

1. warm cache를 만든 뒤 PNG 하나를 다른 유효한 PNG로 교체하고 크기 또는 mtime이 반드시
   바뀌었는지 확인한다.
2. 새 파일 하나를 추가하고 기존 파일 하나를 삭제한다.
3. MEDIA 재진입에서 변경·추가한 두 항목만 판독되고 삭제 항목이 cache에서 제거되는지 확인한다.
4. 캐시 파일이 하나로 유지되고, 전체 5,000개를 다시 판독하지 않는지 확인한다.
5. sentinel 예상 순서와 화면 표시가 한 번만 완성되는지 확인한다.

### E. 검색과 취소 경합

다음 항목을 각각 독립 실행한다. 검색 자체는 촬영 시각 캐시를 읽거나 쓰지 않아야 한다.

1. 차가운 MEDIA 분석 중 검색 시작
2. 검색어 A를 입력한 직후 B로 변경
3. 검색 결과가 부분 표시되는 동안 검색 닫기
4. 검색 취소 뒤 MEDIA 복귀
5. MEDIA → LIST → MEDIA 빠른 연속 전환
6. 위 동작 중 파일 추가로 `PathObserver` 이벤트 발생

각 실행에서 이전 검색어 결과와 취소된 MEDIA 결과가 adapter에 게시된 횟수는 0이어야 한다.
검색 취소 뒤에는 5,000개 목록이 복구되어야 하며, 검색에 의한 cache read/write도 0회여야 한다.
이미 대기열에 들어간 이전 MEDIA 저장과 검색이 만든 쓰기를 혼동하지 않도록, writer가 비어 있는
LIST 상태에서 검색 단독 시나리오도 실행한다.

### F. MEDIA 완료 직후 강제 종료

캐시 저장은 MEDIA 목록 게시와 별도 작업으로 실행될 수 있으므로 다음 두 경우를 나눈다.

1. MEDIA가 처음 보이는 즉시 앱을 강제 종료한다. 재실행 때 캐시가 없거나 미완성이어도 안전하게
   다시 분석하고 정상 목록을 보여야 한다.
2. 캐시 파일이 생기고 크기와 mtime이 안정될 때까지 제한 시간 안에서 기다린 뒤 강제 종료한다.
   재실행에서는 디스크 cache hit, 원본 판독 0회를 확인한다.

두 경우 모두 잘린 캐시 때문에 앱이 멈추거나 목록을 잃어서는 안 된다.

## 6. 자동 테스트 보강

현재 코덱 단위 테스트만으로는 LiveData와 화면 전환의 순서를 확인할 수 없다. 다음 테스트를
추가한다.

- Repository: warm hit 0회 판독, 한 항목 변경 1회 판독, 취소된 세대 저장 금지
- ViewModel/LiveData: 검색 중 include=false, 이전 source의 Success/Failure 차단
- Fragment/Adapter: MEDIA 준비 중 잘못된 MEDIA frame 0회, 완료 뒤 표시 1회
- 전환: LIST→MEDIA→LIST, 검색어 A→B, 검색 닫기, 뒤로가기와 회전 시 위치 보존
- 저장: MEDIA 게시 직후 종료와 AtomicFile 복구

## 7. 최종 판정 기준

- LIST에서는 촬영 시각 원본 판독과 캐시 read/write가 모두 0회다.
- warm MEDIA와 앱 재시작 뒤 MEDIA에서는 원본 판독이 0회다.
- 부분 변경은 변경·추가된 항목만 판독한다.
- 잘못된 MEDIA 순서가 한 프레임도 노출되지 않는다.
- 취소된 검색·MEDIA 결과가 나중에 나타나지 않는다.
- 캐시 저장 중 종료해도 다음 실행에서 안전하게 복구한다.
- Activity 시작 시간과 UI 완료 시간, 자동화 도구 비용을 구분해 보고한다.
- 에뮬레이터 결과는 기능 판정에 사용하고 최종 속도는 Fold 7에서 다시 측정한다.
